# 设计文档模板

> 大需求、Epic、用户可见流程或跨模块功能在更新功能蓝图和创建任务前使用。按实际类型保留产品设计、交互设计或技术设计章节；不适用的章节写明理由，不要静默删除。

---

```markdown
# <功能/产品名称> 设计文档

## 文档信息
- 状态：草案 / 已确认 / 已废弃
- Owner：Human / 团队
- 来源需求：#N
- 对应功能模块：<功能蓝图路径>
- 最后更新：YYYY-MM-DD

## 背景与问题
- 用户/业务/工程遇到什么问题，为什么现在要解决。

## 目标
- 做完后可观察到什么结果。

## 不做
- 本次明确不覆盖什么，防止范围蔓延。

## 用户、场景或调用方
- 目标用户、关键场景；纯技术模块写调用方和上下游。

## 产品流程 / 信息架构
- 页面、入口、主路径、返回路径；不适用时说明原因。

## UI/UX 风格确认（原型前门禁）
- 状态：待讨论 / 讨论中 / 已确认 / 不适用。
- 一句话记忆点：用户第一次看到产品后最应记住的感受或特征。
- 风格关键词：3–5 个；反向关键词：明确不要的 3–5 个。
- 原生与品牌：平台原生感和品牌个性的比例与理由。
- 信息密度与层级：紧凑/舒展、内容优先级、留白和导航姿态。
- 视觉方向：字体、色彩、材质/层次、图标和动效方向；此阶段可不锁死全部 token。
- 参考与反例：参考产品/作品及借鉴点；明确反例及拒绝原因。
- 无障碍底线：深色模式、动态字体、对比度、VoiceOver、Reduce Motion 等。
- 决策记录：决策人、确认日期、适用范围、版本和待确认项。
- 既有规范：复用的 `DESIGN.md` / 品牌规范 / 设计系统路径与具体章节；没有则写“无”。

> 需要原型时，本节状态必须为“已确认”。状态为“待讨论/讨论中”时，不得启动低保真或高保真原型；不适用时必须写明该功能没有用户界面的原因。

## 原型与 UI/UX
- 低保真原型、高保真设计、状态、文案和无障碍要求；必须引用上方已确认风格结论，不适用时说明原因。

## 技术方案
- 架构、模块边界、关键取舍和依赖。

## 数据与接口
- 数据模型、格式、API、同步、版本和兼容规则。

## 状态、错误与恢复
- 正常、空、加载、处理中、失败、离线、权限受限、冲突和恢复。

## 隐私、安全与合规
- 权限、敏感数据、保留/删除、加密、许可和审核要求。

## 验收标准
- [ ] 可观察、可检验的产品/技术结果。
- [ ] 关键边界和失败路径。
- [ ] 不退化与兼容要求。

## 待确认项
- 仍需用户/负责人决定的事项；不要把 TBD 写成既定事实。

## PM 追踪关系
- 来源 requirement/bug：#N
- 功能蓝图：<模块 / 功能点>
- 交付任务：待功能蓝图确认后填写
- 目标里程碑：待任务清单成形后填写
```

## 关联原则

- 大功能只需在顶层 requirement 和对应大模块关联主设计文档，子功能默认继承。
- 子功能有独立流程、接口或风险时，再关联专门文档或主文档具体章节。
- task 必须引用执行所需的具体文档和章节。
