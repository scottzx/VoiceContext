## 2. 背景、目标与成功标准

产品已经能可靠录音、进行本地 ASR、发布开放文稿，并把录音文字交给完整 Agent。待办页已连接系统提醒事项并具备新增、编辑、完成 / 恢复、删除、来源筛选、日历展示和外部变更刷新。当前缺口集中在模块之间：一份文稿是否完整、一次整理用了哪个版本、结果是否真正完成、建议如何成为已创建的系统事项，以及删除后各副本是否一致。

本需求面向录制个人想法、对话或会议后需要整理和执行下一步的用户。个人录音与会议沿用同一 Recording 层级；会议语义增加纪要、决策和参与人等信息，不引入另一套录音状态机。

目标是让用户从一份录音持续追踪到可验证的结果：

1. 重转写、失败恢复和音频过期不会悄悄抹掉已经校对的文字。
2. 用户能区分“处理队列结束”与“文稿完整”，知道缺失范围。
3. 纪要和导图能找到固定来源版本，原文更新后能识别旧结果。
4. AI 提取的建议经过具体确认后才写入系统提醒事项，结果不明时不重复创建。
5. 从纪要、导图节点和系统事项能回到来源文字与可用音频；音频不可用时仍能定位文字。
6. 隐私说明与实际输入范围一致，删除不会留下仍被自动桥接的原文副本。

成功标准以第 10 节的案例验收为准；编译通过、工具返回成功或出现一个文件，均不能单独证明完整闭环已经完成。

### 4.1 F01：重转写保护与文稿完整性

当前整份重转写会以 `clearTranscript: true` 准备处理，随后清除 segments；详情编辑文案却承诺人工修改“永久锁定防覆盖”。当前恢复流程还存在不可读音频任务以 `unreadableAudioSkipped` 终结的情况；这可以避免永久卡住，但不能据此宣称原文完整。

需求：

- 重转写前检查所需音频是否存在且可读，明确可处理范围。音频已过期或全部不可读时不得先清空旧文稿。
- 保留旧文稿与人工修改信息，新的 ASR 结果作为候选版本产生；默认不得覆盖校对文字。整份替换等破坏性选择必须清楚呈现影响并由用户明确选择，具体比较 / 采纳交互待评审。
- 粒度重试只处理失败或指定来源范围，不破坏不相关的已成功内容；重试失败继续保留可阅读的旧版本。
- 分离处理状态与内容完整性。任务成功、不可读跳过、正常静音、有声但 ASR 输出为空、捕获中断、等待处理和音频清理都需有真实原因；正常静音、有声识别失败和音频损坏不能共享一个“完整”结论。
- 公开文稿及 AI 输入携带已知缺口与不确定范围。纪要的状态和范围说明应采用处理状态与完整性共同判断，不单看 `state=complete`。处理已结束但有不可恢复缺口时，允许用户主动生成明确标注“含缺失的纪要”，不因缺口永久阻止整理；缺失内容不得补写为事实。
- 沿用既有 segment ID / source ranges；无法稳定映射的新识别文本不得假装继承旧人工校对。

### 4.2 F02：固定来源版本、统一产物协议与 Skill 兼容

当前融合草稿包含 recordingID 与要求标注 revision 的文字，但没有绑定实际 revision；Source 在文稿更新和回前台时会重新覆盖。产物页只看目录中文件是否存在，不校验来源和完成状态。

需求：

- 创建整理请求时固化一份 canonical JSON 输入及其 recordingID、revision、hash、完整性信息；同一运行始终使用该份快照。不得混读不同时间的 JSON / Markdown 或 Meetings 副本。
- 复用现有 Agent run / session；增加最小关联清单即可，不要求另起通用任务调度系统或大型数据库。
- 用统一产物清单区分纪要、导图、行动建议、导出文件及工作中的临时文件。只有来源校验、格式校验和提交完成的产物进入正式结果列表。
- 临时写入与完成提交分离；提交失败、被取消或中断时不得以文件存在声称完成。重试应能复用已完成阶段，保留成功历史版本。
- 新文稿 revision 产生时保留旧产物并标注“来源已更新”；重新整理必须绑定新版本，不静默覆盖旧结果。
- 统一融合 Skill 与公开 `generate-meeting-minutes` 的规则。公开 Skill 现写输入会议目录下的 `generated/`，融合版要求 `Generated/<recordingID>/`；应提供明确输出适配与索引，不能让 Agent 把最终产物写进 Source。
- 公开 Skill 对 complete / meeting 的要求继续用于正式会议纪要；complete 只表明处理已终结，仍需展示完整性和缺口。处理已结束但不完整时可按用户意图产生“含缺失的纪要”；个人录音或仍在处理中可明确产生“临时整理”，不得伪装为完整原文的正式纪要。
- 保留用户模板和用户编辑过的 Skill，不通过安装更新无提示覆盖它们。

### 4.3 F03：会议整理流程、纪要语义与长文覆盖

需求：

- 录音详情提供容易找到的整理发起与结果入口。建议通过原生 Sheet 选择“会议纪要 / 思维导图 / 行动建议”、模板与输入范围，再进入现有聊天草稿；具体入口层级和布局待交互评审。
- 发起前显示来源版本、当前文稿状态、已知缺口与所用模型服务；无模型、无文字或格式不支持分别给出已有设置 / 返回 / 重试入口。
- 保持用户主动发送原则；已经明确授权的具体操作不应因流程设计强制重复确认。模型输入范围的首次说明与以后偏好如何保存待评审。
- 整理中显示实际运行状态，允许返回录音、打开关联聊天和停止处理；切换 Tab 后仍能找回进行中的运行。
- 纪要至少区分主题 / 摘要、讨论要点、已明确决策、行动建议和未解决问题。内容结构可由模板定义，证据及不确定性规则不可由模板绕过。
- 不把讨论方案写成决议，不把疑似说话人写成确认身份，不把提到的人自动当负责人。未明确负责人或日期时保留空值 / 待确认。
- 段落和关键决策支持结构化原文引用；点击能定位逐字稿并在音频仍可用时回听。
- 长会议信息按稳定 segment / 时间范围分段读取与合并；记录已覆盖范围和未覆盖范围。通用 `file_read` 已有分页能力，本次增加会议语义的覆盖核对，避免摘要仅代表文件开头。
- 结果支持查看、分享、打开关联聊天、选择历史版本及基于新版重新整理。无产物、格式损坏、生成失败和来源已删除分别呈现。

### 4.4 F04：思维导图树与节点来源

需求：

- 以结构化树作为权威导图数据，节点有稳定 ID、标题、可选说明、子节点与来源引用；原文时间范围、来源版本和不确定性遵循 F02 / F03。
- 首轮以原生可折叠层级预览满足查看和定位，不把自由画布、节点拖拽和多人协作作为交付前提。用户若要求图形画布，在交互评审中明确本轮边界。
- 导图支持从主题到讨论、决策、行动建议等分支；节点类型和分组提案由设计评审确定，不能将层级本身误解释为原文中的因果关系。
- 点击节点来源能回到文字 / 音频；行动建议节点可进入 F05 确认流程。
- 支持导出 Markdown 及一种约定的图形 / 图描述格式；具体格式待评审，不把通用文件预览等同于导图交互已实现。
- 结构校验失败、循环 / 引用损坏、超深层级或未完成输出应诚实失败或降级为可读内容；生成失败不得影响原文与已完成纪要。

### 4.5 F05：行动建议的具体确认

需求：

- 将 AI 候选建议作为独立状态呈现，不能用系统事项样式让用户误以为已经创建。
- 每项展示可编辑标题、负责人信息、到期日期、可选时间、独立定时提醒、目标系统列表、备注与原文来源；负责人仅为来源事实，不隐含给他人分配权限。
- 未明确日期不得猜日期；“下周”等相对表达必须依据原文发生时间和时区解析并展示解释，不默认按生成当天换算。无法确定时请求用户补充或保存为无日期事项。
- 用户可选择一项或多项确认创建、修改、忽略。一次明确确认即可授权所显示的具体事项；不得创建未选择或确认之后被悄悄修改的内容。
- 重复生成后的相似建议需展示已关联结果或可能重复，允许用户明确“这是另一件事”；不能只按标题相同就自动合并合法的不同事项。
- 批量创建逐项回报成功、失败与结果待核实，成功项保持已创建状态；重试只针对未完成项。
- 取消确认不产生系统写入。权限拒绝或无可写列表时保留候选，可授权 / 换列表后继续。

### 4.6 F06：录音与系统事项的来源关联及幂等

需求：

- 保存候选 action ID、来源 recordingID / revision / artifact ID / 引用位置与系统 reminder ID 的关联；不把系统事项内容和完成状态另存为第二权威副本。
- 从录音 / 整理结果能查关联事项，从本 App 的系统事项详情能回来源；系统提醒事项中的来源链接或备注方案需兼容 EventKit，具体载体待技术评审。
- 每次确认写入有稳定 request ID 和可恢复日志；同一确认双击、网络 / IPC 中断、App 重启与 Agent 重试均不得盲目重复创建。
- 先记录写入意图，写入成功后读取系统对象并保存关联。写入结果不明先查询、核对来源标记与已有映射；无法核实时呈现“待核实”并让用户选择，不用名称模糊匹配后自动补建。
- 幂等针对同一已确认操作；用户明确创建另一件相同标题的事项时，新的 action / request ID 可生成独立事项。
- 权限撤销、系统对象被外部完成 / 修改 / 删除、列表删除或 ID 失效分别处理。刷新真实系统状态，不让缓存复活已删除事项。
- 录音来源删除时，默认不删除系统提醒事项；关联显示来源已删除并按 F08 处理。系统事项删除也不得删除录音、文稿或其他产物。

### 4.7 F07：UI 与提醒工具的统一契约

需求：

- UI、Agent 与 CLI 使用相同的列表解析、日期 / 时区、提醒与写入回执规则；复用既有 EventKit 能力，不重写通用待办页面。
- 增加按系统 list ID 的精确目标选择。传入 ID 无效、无权限或列表只读时失败；传入名字有多项匹配时要求明确选择，不按模糊匹配任意选第一项。
- 用户明确指定的列表不存在时不得静默落到默认列表。只有用户未指定列表时，才按已显示的默认规则选系统默认可写列表。
- 到期日期和定时通知独立。`--due` 只代表到期属性；若工具支持独立时间提醒，应有明确参数 / 字段和实际 alarm 回执，具体参数名待技术评审。
- 成功回执包含实际系统 ID、标题、list ID / 名称、实际到期日期与时区、实际提醒设置及 request ID；结果来自保存后的系统对象，不仅回显请求值。
- 对未设置提醒、提醒能力不支持、权限拒绝、只读、无效时间、保存失败和结果不明使用可解析的区别；取消或失败不能报告“已创建”。
- 重复、位置、相对时间、多 alarm 等复杂组合保留既有保护。工具不支持时明确说明，不能降级创建后仍宣称完整满足。
- “已设置定时提醒”与“通知已到达”分开；后者需在系统通知设置下经授权真机验收。

### 4.8 F08：音频保留、删除一致性与输入隐私

需求：

- 原始音频默认保留 7 天、用户可主动长期保留；音频清理不自动删除文字、纪要或系统事项。本文不授权自动延长音频保留。
- 待处理 / 失败任务与音频即将过期的冲突需显式说明。是否临时保护正在处理的音频、保护多久或仅引导用户主动长期保留，由 Human 决策后实现；决策前遵循现行保留时限，并如实记录清理导致的不可恢复范围。
- 重转写必须先执行 F01 音频可用性检查；恢复不能把已被清理的音频当可重新处理的输入。
- 删除录音的确认文案说明音频、canonical 文稿、公开副本、Agent 快照、派生结果和系统事项各自的处理范围。原文及其受管副本删除必须一致，不得在 Meetings / Daily 残留后继续桥接到 Agent。
- 受管原文副本包含 F02 固定的 AI 输入快照、F01 保留的旧校对版本与重转写候选；保留派生结果不等于隐式保留整份原文。删除协调必须清理这些副本，并区分经用户选择保留的摘要 / 导图与原文存档。
- 建议以删除协调服务与可恢复记录维护 canonical store、索引、Meetings、Daily timeline、Source、进行中的运行与关联；源删除完成前撤销该来源的继续读取 / 提交。具体事务与 tombstone 格式待技术评审。
- 单删与批删都应报告真实部分失败；不能吞掉全部错误后宣称所有项目已经删除。重试和前台恢复可继续未完成的受管清理。
- 生成物删除 / 保留的默认选择待 Human 确认。若允许保留，必须用户可理解且显示“来源已删除”，不能继续提供原文深链或重新桥接；默认不删除系统事项。
- 修复已有录音已删、公开副本仍存在的残留。以 canonical recording ID / 删除记录核对，不仅根据目录中文件是否存在判断它是可发布资料。
- 整理前说明所选文字和相关元数据将按用户配置发送给哪个模型服务；本地 ASR、音频本地保存与云模型处理文字不可混为一个“全本地”承诺。
- 默认整理输入限于选定录音快照及明确选择的模板 / 元数据。跨录音查找、附件或音频输入必须属于用户明确的操作范围；通用 Agent 能读取工作区的能力不等于用户授权本次自动读取全部录音。
- 不默认暴露原始音频、凭据、数据库、journal 或声纹 embedding。用户资料中的文字视为内容，不提升为系统指令；来源路径与写入路径要执行现有边界检查并新增格式 / ID 校验。
- 同步与导出范围需逐项说明。受管副本删除不等于能够撤回用户已导出文件或已发往第三方模型的内容，不作无法保证的删除承诺。

## 5. 关键流程与信息架构

### 5.1 主路径

1. 用户在“会议”中录音或导入音频；原录音状态机负责落盘、停止与恢复。
2. ASR 发布文稿，并附处理状态、已知缺口、revision 和时间 / segment 来源。
3. 用户从详情发起整理，选择结果类型 / 模板，确认所显示的输入范围；F02 固化输入版本。
4. 现有聊天草稿接收专属整理请求，用户发送后执行；无可用文字时停止，仍在处理时明确临时整理，处理已结束但存在缺口时可生成明确“含缺失的纪要”。
5. Agent 依据证据生成产物，校验后提交清单；用户可返回录音看到状态与结果。
6. 用户从纪要 / 导图 / 行动建议查看原文出处，选中具体候选，修改信息并确认创建。
7. F06 / F07 执行可恢复写入并核实实际系统结果；成功项展示系统 ID 和来源关联。
8. 待办页沿用现有系统数据刷新；完成 / 修改 / 删除在关联视图同步体现。

### 5.2 原文更新与重转写

用户修改文字或发起重转写时保留上一可用版本；新候选成功并被采纳后生成新 revision。旧纪要 / 导图仍可查看但显示来源更新。用户明确基于新版整理才创建新运行；不能自动更改已创建事项的标题、日期或提醒。

### 5.3 中断与结果不明

ASR、AI 运行和系统写入分别恢复。ASR 失败保留原文；AI 中断保留输入快照及已提交结果；系统写入中断先查询回执 / 来源标记，再处理候选状态。三种重试不得共用一个模糊“再试一次”按钮而忽略副作用。

### 5.4 删除

删除前明确对象范围 → 取消关联运行并标记来源不可继续使用 → 清除受管原文及副本 / 更新 Daily → 处理产物与关联的已确认保留策略 → 记录结果与可恢复失败。系统事项默认保留。后续刷新不能把历史残留重新当原文发布。

## 6. UI/UX 风格确认与交互评审

## 7. 数据、接口与权威来源

### 7.1 保持的既有权威

| 数据 | 权威来源 | 补充边界 |
| --- | --- | --- |
| 录音 / 音频与处理任务 | 原 Recording repository 与录音服务 | 不绕过 journal、保留和恢复规则 |
| 逐字稿 | canonical `TranscriptDocumentV1` 与文稿服务 | 原文编辑仍走 revision / 索引 / 镜像一致的业务服务 |
| Agent 对话与运行 | 现有 Agent Store / session / run | 新增专属关联，复用运行能力 |
| 系统事项 | EventKit / 系统提醒事项 | 本 App 只保存来源和必要可重建缓存，不另存完成状态权威 |
| 派生文件 | 独立 Generated 存储及产物清单 | 不覆盖原文；提交完成后才作为正式产物 |

### 7.2 提案字段

以下为逻辑契约草案。命名、schema 版本、文件布局和存储载体须经技术评审，不应直接当作已经发布的格式。

| 对象 | 最小提案字段 | 约束 |
| --- | --- | --- |
| 整理输入 / 请求 | request ID、recording ID、source revision / hash、canonical schema、输入快照路径、完整性、缺口范围、模板 ID / version、结果类型、模型配置引用、创建时间 / 时区 | 不保存凭据；固定快照不可被 Source 刷新覆盖 |
| 运行关联 | run ID、session ID、request ID、recording ID、状态、阶段、实际错误、更新时间、已完成阶段 | 复用 Agent 状态，不凭 UI 推测完成 |
| 产物清单 | artifact ID、type、schema / version、source recording ID / revision / hash、run / session ID、生成时间、template ID / version、文件相对路径、状态、coverage、warnings、citations | 路径在受管 Generated 内；完成提交前校验 |
| 引用 | recording ID、revision、segment IDs、start / end sample 或时间范围、可选摘录 | 引用来源必须属于绑定快照；可解析且能定位 |
| 内容完整性 | processing state、completeness、known gaps、已覆盖 / 待处理范围、原因 | 具体编码待评审；不得仅由队列为空推断完整 |
| 导图 | map ID、artifact ID、根节点、node ID、标题 / 说明、children、引用、可选 node type、uncertainty | 无环、ID 唯一、节点引用可验证；深度 / 大小上限待评审 |
| 行动候选 | action ID、source artifact / revision、标题、owner fact / uncertainty、due、alarm、timezone、list ID、备注、引用、候选状态 | 空值与“不确定”明确区分；AI 不猜缺失字段 |
| 写入意图 / 关联 | request ID、action ID、已确认内容 hash、来源、目标 list ID、状态、system reminder ID、实际回执、时间、错误 | 同一确认幂等；明确另建时产生新 ID |
| 删除记录 | recording ID、范围、策略、时间、各受管对象进度、失败与重试信息 | 具体 tombstone / 事务格式待评审；用于阻止残留再发布 |

现有 `voice-context/transcript@1` 和公开脚本生成的 `voice-context/meeting-minutes@1` 保持可读；新增字段是否可在 @1 兼容增加、完整性是否需另设版本，由兼容评审确定。不要把本表的新字段伪称现有 schema 必填字段。

### 7.3 最小接口职责

- 文稿预检 / 候选版本服务：验证音频、保存旧版本、产生新候选、明确采纳和 revision。
- 整理服务：固定输入、关联现有运行、提交 / 校验产物、比较来源版本和恢复状态。
- 引用解析：定位已绑定版本的 segment / 时间，音频不可用时保留文字定位。
- 行动确认 / 写入服务：接受具体已确认 payload、记录幂等意图、调用统一提醒契约、核实并保存映射。
- 删除协调：撤销来源读 / 写，清理与重建各受管副本，按已确认策略处理产物 / 关联并恢复失败。

这些是职责边界，不要求每个职责新建一个架构层。实现应优先复用已有业务服务并保持最小改动。

### 7.4 兼容与升级

- 旧文稿没有新完整性字段时标为“完整性信息未记录”，结合已有任务与 gap 证据核对；不得自动补成“完整”。
- 旧 `Generated/<recordingID>/` 文件可继续预览，但无可验证来源时标为历史文件，不能伪造来源 revision 或已完成 run。
- 旧 `Meetings/.../generated/<template>/<timestamp>.md` 使用来源头导入 / 索引到统一结果入口；路径不规范或来源头损坏时给出降级说明。
- 保留用户编辑过的 Skill / 模板；更新采用可辨别的迁移或独立适配，不强制覆盖。
- 不改变既有 Bundle ID、数据容器或系统 reminder ID；兼容检查涵盖未升级文稿、跨版本 Generated 和用户模板。
- 幂等日志、映射和删除记录需要升级 / 崩溃恢复；迁移必须可重复执行，不复制系统事项。

## 8. 状态、错误与恢复矩阵

| 对象 / 条件 | 用户所见 | 可执行动作 | 禁止行为 |
| --- | --- | --- | --- |
| 文稿无文字 / ASR 处理中 | 显示真实处理状态与已有范围 | 查看进度、返回、可用时重试 | 空内容冒充纪要；自动清旧文稿 |
| 队列结束但有不可读 / 丢失范围 | 文字可阅读，明确“不完整”及原因 | 阅读、临时整理、可恢复时重试 | 只因 job completed 宣称完整 |
| 音频已过期 | 原播放器位置解释音频不可用，文字保留 | 定位文字、整理现有文字 | 先清文稿再发现无法重转写 |
| 重转写候选失败 | 旧版本仍可阅读，新候选失败 | 按可用范围重试 | 隐藏 / 丢失人工校对版本 |
| 未配置模型 | 复用模型配置入口 | 配置、返回 | 发起无法执行的运行并显示生成中 |
| AI 运行中 / 中断 | 展示实际阶段或待恢复 | 打开聊天、停止、恢复 | 把临时文件视作完成结果 |
| 产物完成 / source revision 更新 | 可查看；旧结果显示来源已更新 | 引用、分享、历史、新版整理 | 静默覆盖或自动改系统事项 |
| 产物格式 / 来源校验失败 | 显示无法作为正式结果，必要时降级预览 | 重试、查看实际文件 | 伪造 provenance |
| 候选 / 未确认 | 标明行动建议与缺失信息 | 编辑、选择、确认、忽略 | 自动写系统提醒事项 |
| 写入成功 | 显示实际系统事项及关联 | 在待办页查看 / 编辑 | 以请求值替代实际结果 |
| 写入失败 / 权限拒绝 / 只读 | 保留候选与明确错误 | 授权、换列表、针对失败项重试 | 报告已创建；静默换默认列表 |
| 写入结果不明 | 标记待核实并先查询 | 查询、人工核对 | 盲目重复创建 |
| 系统事项外部变更 / 删除 | 显示系统真实状态或关联失效 | 刷新、另建需明确意图 | 用缓存复活事项 |
| 来源删除 / 部分删除失败 | 来源已删或清理未完成，范围可读 | 按策略保留结果、重试清理 | 从残留 Meetings / Daily 再发布 |
| 离线 | 区分本地文稿可用与模型服务不可用 | 本地查看、等待 / 重试 | 统一错误文案掩盖数据仍在 |

状态名称为产品语义，不预先强制重写已有枚举。运行状态、文稿完整性、来源新旧和系统事项状态是不同维度，不能压缩成一个“完成”标签。

## 9. 隐私与资源约束

录音可靠性仍高于 AI 计算、文件导出和工具执行；沿用既有音频协调，录音期间不再次启动麦克风或播报。并发负载与后台恢复需要真机证据，本文不凭代码存在承诺无限后台生成。

当前桥接复制多个公开文字目录到通用工作区，是副本而非不可写安全挂载。新增整理流程应默认只准备本次选定输入，保留边界检查，并向用户说明通用 Agent 的更广文件能力；不能以提示词“不要修改”替代产物来源校验或公开文稿业务服务。

每条引用、导图节点、行动候选与写入日志只保存完成来源追溯必要的数据。日志不记录凭据或不必要原文；生成物和关联的同步 / 备份 / 删除范围须在 F08 技术与隐私评审中确定，不能默认为与原文同一 iCloud 镜像。

## 10. 验收案例

以下案例同时用于交互评审、业务回归与授权后的真机验收；测试项状态目前均为待执行 / 待补证据，不表示功能已交付。

| 案例 ID | 功能 | 场景及通过条件 |
| --- | --- | --- |
| F01-AC01 | F01 | 已校对 segment 发起整份重转写：旧文稿与修改信息保留；新结果不得默认覆盖人工文字，采纳选择符合已评审交互 |
| F01-AC02 | F01 | 音频已过期 / 不可读时重转写：先提示实际可用范围；没有可处理音频时旧文稿仍可阅读，不能先清空 |
