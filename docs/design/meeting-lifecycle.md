## 2. 目标与边界

让参会者能够回答四个问题：这场会为什么开；我应该带什么、问什么；会上实际说清了什么；接下来我要做什么或跟进什么。

主路径：在聊天中提供通知 → 智能体提取并核对必要信息 → 创建 Yima 会议及对应日程 → 日历中打开同一日程及会议来源 → 记录讨论 → 在聊天中整理会议 → 确认个人行动 → 创建 Yima 待办 → 跟进并回看来源。系统接入独立于本地创建，会前资料与问题逐步丰富同一上下文。

首轮应包含 Yima 本地日程/待办、每会议一个日程、聊天中的通知提取与日程创建、既有录音/逐字稿引用、会后整理与个人待办创建、会议列表及提醒页共享入口和反向来源关联。系统列表接入与同步另外设计；独立会议概览、完整首页重排和专属准备页后续评审。附件入口复用现有能力；图片 OCR、复杂表格识别和多来源自动汇集另行确定，不把现有文件预览视为已支持内容解析。

组织者拟定/发布通知、邀请与签到、向他人派单、多人协作审批和项目管理不属于本轮范围。个人助手可以记录别人负责的事情，也可以提醒用户跟进；这不表示已经把任务分配或通知给对方。

## 3. 一场会议贯穿四个阶段

| 阶段 | 主要输入 | 应沉淀的内容 | 完成这一阶段后用户知道什么 |
|---|---|---|---|
| 会前通知 | 通知原文、用户补充 | 主题、计划时间/地点、目的、议程线索、被邀请人员及待核对项 | 为什么参加、何时何地、哪些信息还不可靠 |
| 会前准备 | 已核对的通知、我的角色、主动选择的资料 | 要读的材料、要带的案例、要问的问题、希望获得的答案 | 我怎样带着目的参加 |
| 会议讨论 | 录音、逐字稿、人工笔记、现场材料 | 讨论事实、问题回答、意见分歧、决定、未决问题和行动候选 | 哪些问题已说清，哪些尚未解决 |
| 会议待办 | 已核对的决定/承诺、用户选择 | 我负责的行动、我跟进的事项、来源与系统提醒关联 | 下一步做什么、跟谁确认、怎样回看依据 |

内容不随阶段替换：原通知、准备、过程证据和会后结果均可回看。会前问题可以在会中补充，会后未决问题也可以成为后续准备。

始终区分：通知中的计划、AI 的建议、会议中的提议、实际确认的决定。日程结束不代表逐字稿完整，纪要生成不代表行动完成。

## 4. 样例：通知如何成为可用上下文

### 可直接整理的内容

| 内容 | 从样例得到的信息 | 处理规则 |
|---|---|---|
| 主题 | 方案共创机制宣贯 | 保留通知原意 |
| 计划时间 | 5 月 22 日 13:30–14:30 | 年份和时区未给出，不能转换为确定日程；不按当前年份推定 |
| 地点 | 西溪科创园一楼大会议室 | 保留原地点，不补楼栋、地址或地图定位 |
| 目的 | 提升方案质量、发挥方案团队与技术体系协作价值、为后续交付清除疑难点 | 归纳为通知所述目的，不表示效果已经实现 |
| 内容线索 | 工作机制宣贯，以及产品/技术交流与现场答疑 | 不是带精确时长的正式议程 |
| 参会信息 | 多角色、业务条线和梯队的支撑人员表 | 文本存在乱码与列关系丢失；名单与对应关系需要核对 |

原文中的业务、业务架构、技术架构、数据架构、大产品经理等可作为角色线索；“系統梨构”等疑似错误保留原文并标注待核对。姓名、业务、角色、梯队不能靠相邻行拼成确定关系，也不能凭姓名自动认定“我”。

被列入通知的人是被邀请或拟定的支撑人员，不能直接记为实际到场者，也不能自动绑定逐字稿里的说话人。原文仍需可查看，用户修正的是结构化解释。

年份未确定时，仍可以保存通知、会议及对应的待安排 Yima 日程；日期确认后更新原日程，才具备导出系统事件的条件。人员表未恢复不阻断建立个人日程。用户仅提供通知时可先展示提取结果及“创建日程”；用户已明确要求创建且字段充分时，复用该创建意图，仅针对缺失或歧义字段补充确认，不要求再次发出同义指令。不自动发送邀请，日程提醒与会后待办的定时提醒分别设置。

### 用户可补充的少量信息

- 我以什么角色/业务身份参加？不知道时先保留通用准备。
- 我最希望这场会说清什么？可从建议问题中选择，也可自行输入。
- 是否有机制草案或相关材料？没有时显示未提供，不假装已经读过。

## 5. 会前准备：准备有价值的参与内容

准备分为“了解背景、带上材料、提出问题、明确期望”，建议内容与用户选定的个人准备分开。清单可以完成，准备问题可以标记已准备；均不自动写入系统提醒事项。

针对样例，下面是根据通知提出的准备建议，不是通知已经给出的规则：

| 准备方向 | 可带入会议的问题 | 如已有材料，可准备什么 |
|---|---|---|
| 共创触发条件 | 什么规模、复杂度或风险的方案必须进入共创？谁发起？ | 一个需要跨团队支撑的实际案例 |
| 角色与责任 | 业务、业务架构、技术架构、数据架构、产品各自交付什么？ | 自己职责中的协作困难；核对自己的条线与支撑人员 |
| 输出与评审 | 共创要形成哪些材料？由谁评审、确认质量？ | 当前方案模板、评审问题；没有模板则列为待索取 |
| 分歧处理 | 产品能力不满足或技术判断冲突时，谁决定、怎样升级？ | 一个产品边界或技术选型疑问 |
| 交付衔接 | 怎样把共创结论、风险和遗留问题交给交付团队？ | 一个因交接不清造成返工的案例 |
| 机制执行 | 宣贯后何时适用？例外和反馈如何处理？ | 需要现场确认的执行条件 |

根据用户选择的角色，从上述问题中优先挑出 3–5 个。技术角色可优先关注能力边界、评审和分歧；产品角色可优先关注需求边界、产品能力和输出。未确认角色时不替用户选身份。

建议的个人期望是：会后能说明如何发起共创、自己承担什么、去哪里取得规则和模板、疑难问题找谁处理。它们是待获得的答案，不能提前填成既定制度。

AI 准备使用已核对的通知和用户明确选定、实际可读取的资料。附件只有预览能力时，应说明尚未读取其内容；不声称了解未提供的公司产品或技术资料。

## 6. 会议讨论：逐字稿支撑结果，而非代替结果

复用既有录音、转写、说话人核对、编辑和缺口提示。录音可以立即开始，创建会议、补资料、填写角色或准备问题不能成为开录前置条件。过程中允许简短人工标记问题、决定或行动线索；不要求用户不停维护会议表单。

会后按会前问题组织结果，并支持实际新增的议题：

- 问题与回答：把准备问题关联到回答证据；区分已回答、部分回答、未找到回答。文稿有缺口时显示“现有记录未找到，完整性不足”，不能断言会上没讨论。
- 讨论与分歧：记录不同观点、条件和风险，不把所有发言折成一致意见。
- 决定：说明已确定的内容、适用条件和依据。提议、意向、待审批和互相冲突的表述不能自动记为最终决定。
- 未决问题：说明还缺什么信息或决定；没有负责人时保持未明确。
- 行动候选：仅从真实承诺、明确安排或用户补充中形成；通知中的“拟定机制”不能推出“机制已通过”或具体会后派工。

AI 生成内容是待核对结果，用户确认后记录确认状态。用户人工补记没有录音依据时标明人工补充，不制造时间戳。关键结果可回到对应逐字稿片段、可用音频或人工笔记。

针对本通知，会后应检查：触发条件、角色分工、产出与评审、分歧升级、交付交接、执行与反馈这六类问题是否有答案。用户未提供会议讨论，本轮不能填写实际答案、决定或待办。

## 7. 会议待办：我的行动与我的跟进

| 类型 | 内容含义 | 个人助手的处理 |
|---|---|---|
| 我负责 | 已确认由用户执行的动作 | 用户确认标题与设置后可创建 Yima 个人待办 |
| 我跟进 | 他人负责、但用户需要确认进展的动作 | 可创建“向某人确认……”的个人提醒，保留原业务负责人与自己的跟进职责 |
| 尚未落实 | 有行动方向，但负责人/范围等未明确 | 留在候选或未决区；不装作已分派 |
| 准备建议 | 会前阅读、带案例、准备提问 | 保持建议或个人准备；用户主动采纳后才进入跟进 |

每项候选应说明：动作和期望产出、原文提到的负责人、日期（可缺失）、前置条件（如有）、来源、当前确认/关联状态。例：“了解机制”仍是目标；用户若明确采纳，可以细化为“索取机制草案并核对共创申请流程”。不能仅因它看起来合理，就说会议已经安排了这个任务。

负责人和日期缺失时如实显示。没有日期的个人事项仍可创建；相对日期要结合经确认的实际会议日期解释，不能基于当前日期或未确定年份猜测。

Yima 自有待办由 App 保存内容与完成状态，无系统授权也能使用；非 Yima 系统来源仍由 EventKit 管理，可选系统镜像按待确认的同步契约接入。会议保存来源关系，复用候选确认、真实回执和幂等原则。完成“向某人确认进度”的个人提醒，不代表对方的业务行动已经完成。

个人准备清单是会议资料中的检查项；Yima 待办是用户明确选择持续跟进的事项。两者不自动复制。一次确认创建后，聊天、会议和提醒页打开同一个 Yima 对象，系统镜像在 App 内去重显示。

## 8. 产品组织与数据边界提案

用户已明确每个会议对应一个日程：会议与 Yima 日程形成稳定的一对一关系，没有录音时也能承载通知和准备，随后关联既有 Recording。不创建空录音伪装成未来会议，也不建立第二套录音状态机。新增数据关系已确认产品范围，具体契约与迁移仍需技术评审。

会议内按通知/准备、过程记录、会议结果、个人跟进组织内容；沿用现有四 Tab。会议列表如何展示未来会议与历史录音、无录音会议如何进入详情，留给信息架构评审，不直接改变已批准的首页和录音详情。

最少关系包含：会议上下文与原通知版本、用户确认的字段、来源聊天/执行记录、唯一 Yima 日程、准备问题、关联录音及文稿版本、结果与依据、Yima 待办关联以及可选系统镜像映射。首轮不把多段独立录音组合、周期会议和自动匹配日历设为完成条件。

计划时间/邀请人员与实际记录时间/已核对说话人分开。修改通知或文稿后，旧准备/纪要显示其来源版本；不会静默把旧结果冒充成基于新资料生成。会议当前安排从关联的 Yima 日程读取；非 Yima 系统来源内容仍由系统管理。

## 9. UI/UX 与交付设计检查

- 风格：复用已批准的 `DESIGN.md`，适用截至 2026-10-04 的决策日志，以及 Typography、Color、Spacing、Layout、Core Components、Accessibility、Prohibited Patterns。
- 记忆点与关键词：打开就知道这场会议当前需要我做什么；原生、安静、内容优先、清楚、可信。避免彩色卡片墙、装饰渐变、密集仪表盘和 AI 宣传装饰。
- 平台感与层级：以原生单列列表、文档和系统 Sheet 为主；系统字体与中性色，红色保留录音/破坏性语义。录音证据详情继续先播放器、后逐字稿；根页面和次级页面的 Tab 显隐遵循现有规范。
- 参考：Apple Voice Memos 的记录层级、克制与开录入口；系统提醒事项的个人任务操作。拒绝把会议内容堆成多列企业看板或每段一张彩色卡片。
- 无障碍：44pt 命中区、动态字体、深色模式、VoiceOver 可读的字段核对与来源状态、Reduce Motion；不只用颜色区分计划、建议、决定与完成。
- 决策：Human 为决策人；复用既有风格批准记录。本轮确认的是参会者范围及聊天/日历/待办联动效果，会议新增导航、内容密度和状态交互仍为草案。本轮不制作原型。

后续需交付：信息架构与关键流程、字段核对与来源设计、正常/空/处理/失败/离线/权限状态、低保真和高保真适用性评审、无障碍规格、设计走查。实现之前需完成会议载体及迁移、附件读取边界、输入版本和删除关系的技术设计。通知发送、企业派工、购买和新计费流程不适用本轮。

## 10. 状态、恢复与隐私

| 情况 | 预期行为 |
|---|---|
| 通知缺年份、参与表损坏 | 保存原文和已明确内容；逐字段待核对，不阻断通用准备 |
| 没有资料或角色 | 基于通知给通用准备，明确资料未提供/角色未确定 |
| 解析/AI 生成失败或无模型 | 原通知、人工准备和录音仍可用；保留输入，允许重试；不显示已完成 |
| 通知变更或延期 | 保留原版本，重新核对变化；关联的日程/个人提醒分别处理，不静默批量改写 |
| 文稿处理中或有缺口 | 显示实际范围；已有内容可以整理，但结果说明完整性限制 |
| 没有录音 | 可保存人工笔记与人工确认结果，明确来源；不伪装成转写 |
| 行动写入失败或结果不明 | 保留候选，分别报告；结果不明先核对，避免重复创建 |
| 系统权限受限/外部完成或删除 | Yima 本地内容继续可用；显示受影响接入状态；读不到不能推断删除 |

导入和保存会议不自动调用模型、读取全部日历或发送消息。会前/会后 AI 操作说明所选资料范围，遵循用户主动发起和现有模型服务配置。相关文件默认不暴露给 Agent 的旧边界继续适用；要支持资料理解，必须明确选择、内容读取能力、请求范围和清理规则后再实施。

音频继续按既有默认 7 天和主动长期保留规则处理，会议上下文不擅自延长保留。删除会议上下文、删除录音、移除附件和删除系统对象各自的影响需要设计清楚；系统日程/提醒不因来源删除而默认被删。通知原文件不被修改。

## 11. 最小闭环与验收建议

建议先用本通知完成一个完整样例，再扩展导入方式与复杂组织能力：

1. 聊天中粘贴通知并要求创建日程 → 正确提取主题/地点/目的，补充确认缺失年份等必要信息；参与表待核对不冒充确定分工。
2. 创建会议及一个 Yima 日程 → 聊天返回本地保存结果及入口；会议列表和提醒页找到同一对象；可回原通知/聊天；拒绝系统权限仍可使用。用户既有来源筛选被尊重，隐藏来源时仍允许直接打开，不偷偷修改筛选。
3. 从日程关联上下文开始录音或选择已有逐字稿 → 不靠同名自动绑定；临时开录仍无需填表；准备问题可按需补充。
4. 聊天中整理实际会议记录 → 问题答案、决定、分歧、未决与行动有各自含义和依据；没有依据的样例不生成实际决定/承诺。
5. 用户确认我的行动/我的跟进 → 创建 Yima 待办，聊天回执、待办页与会议来源可核对；无系统权限或未给日期的事项仍可创建。
6. 在 App 编辑日程、修改/完成待办 → 相关页面展示同一对象的实际状态；系统接入后的变更按已确认的同步契约另行验收；原通知仍保留原文；完成个人跟进不等同他人业务完成。

边界验收还应覆盖：无录音人工笔记、文稿缺口、通知变更、姓名/说话人未确认、无日期行动、模型失败、权限失败、写入结果不明，以及旧录音数据兼容。禁止 iOS Simulator；运行验收只可在用户明确授权后使用物理设备，本轮仅做文档与静态核对。

## 13. 整体前端交互调整提案

本节回应用户“APP 的整体前端交互需要做什么变化”。以下是推荐的信息架构与交互，尚未批准为最终页面或启动实现。用户随后明确首轮以聊天、日历、待办的联动效果为主，下述独立会议概览、准备页和首页扩展保留为后续提案，不作为第 15 节核心联动的前置条件。继续复用第 9 节的设计风格，不新增底部 Tab，也不更改已批准的四 Tab 顺序。

### 13.1 四个 Tab 的职责

| Tab | 推荐职责 | 需要的变化 |
|---|---|---|
| 聊天 | 通用助手及通知提取、日程创建、会后整理和待办创建的操作入口 | 展示提取结果、实际创建结果、打开日程/待办与来源入口；从会议进入时带所选上下文 |
| 会议 | 过程记录与文稿入口，后续扩展会前准备和会议概览 | 首轮补本场录音/文稿与聊天/日程的关联；未录音会议首页和独立概览后续评审 |
| 提醒 | Yima 日程/待办与授权系统来源的统一视图 | 无授权仍能创建、查看和完成；会议日程可打开同一会议；可选系统镜像去重 |
| 拓展 | 模型、工具与统一设置 | 复用既有配置；从会议配置模型后回原任务，保留输入与所选资料 |

主导航仍为“聊天 / 会议 / 提醒 / 拓展”。根页面显示底部 Tab，次级页面隐藏；会议列表位置、聊天输入、提醒来源筛选和草稿在往返后应保留。

### 13.2 会议首页：能找到待参加的会，也能立即开录

静态读取现有 `Features/Home/ContentView.swift`：当前首页为搜索、筛选/多选、按日期分组的录音列表与日期滚轮跳转，功能菜单管理导入/文件夹/转写任务；本节不把规范里的日历条当成当前源码已实现的月历。

推荐首页保留平铺列表和现有日期分组/跳转，内容分为：

- 即将参加：已确认计划时间的未来会议，按最近时间优先；行展示主题、时间/地点和准备状态。
- 最近记录：既有录音和已发生会议，继续按日期分组；行展示录音/文稿状态及需要用户处理的事项。
- 时间待确认：没有确定日期的通知仍可进入，显示明确文字，不塞进猜测的日期。

同一会议从通知进入录音后仍只有一条会议入口；关联录音作为会议内容，不再在首页重复列出。未关联会议的个人/临时录音继续用现有录音行和详情。日期已过只改变时间排序，不据此认定会议已召开或资料已完成。

首页增加中性的“添加会议”入口，首轮默认粘贴通知，也可手工填写最少信息。录音沿用独立红色快捷入口，仍可以不建会议、不填表立即开始。筛选复用现有 Sheet，扩展会议时间/内容条件；不能叠加多排常驻状态按钮和装饰统计卡片。搜索逐步覆盖会议主题、通知、准备问题、文稿和结果，并在命中项说明来源类型、打开对应内容位置。

### 13.3 新增会议概览，复用原录音详情

推荐增加一层“会议概览”，承载尚无录音时也需要存在的内容；会议列表中的会议行进入此页。原 `RecordingDetailScreen` 继续作为录音证据页面，个人录音直接进入原详情，避免强迫所有录音变成正式会议。

会议概览采用标题/时间/地点、一项当前建议动作和四个平铺内容入口：

| 入口 | 概览展示 | 进入后可以做什么 |
|---|---|---|
| 通知与准备 | 通知核对状态、个人准备问题数量/进度 | 查看原通知、改正字段、选择角色、维护准备清单和问题 |
| 会议记录 | 是否有录音/笔记、实际文稿状态 | 开始本场录音、打开原录音详情、人工补记 |
| 会议结果 | 是否已整理、问题回答与未决概况 | 查看答案、决定、分歧与依据，核对或继续调整 |
| 个人跟进 | 行动候选和已关联个人提醒 | 区分我的行动/我的跟进，确认创建、打开已有系统事项 |

会前优先提示“准备参会”，需要记录时提供“开始本场录音”，已有文字后提供“整理会议结果”，已有关联事项时提供“查看跟进”。这些是建议动作，其他内容入口持续可用；不自动开录或调用模型，不因时钟变化强制切页，也不把生成完纪要等同会议已完成。

当前录音详情已有“逐字稿 / 参会人与声纹 / 详细信息 / 备忘录”四个内容区。保留其职责，不继续向这组分段控件添加通知、准备、纪要和待办。相关文件仍复用已有文件入口，概览引用同一份资料，不复制出第二份附件。录音证据页遵循音频与逐字稿的既有布局；标题与返回文案应区分会议概览和录音详情。

### 13.4 导入与准备：先保存，再逐项核对

导入建议用原生 Sheet：粘贴通知 → 保存原文/解析字段 → 核对明确值与待确认项 → 进入会议概览。退出未保存时的草稿保留或丢弃行为需在详细交互中明确。年份不明不强制猜日期，人员表损坏不强制填全后才能保存。

准备页优先展示“我的身份、我想问的问题、需要的资料”。生成问题是用户主动操作，结果先作为建议，用户保留/修改后进入个人清单。会后同一问题展示答案与依据；新增问题、资料导入失败、模型缺失和保存失败都有可解释状态。

### 13.5 AI 操作与聊天：会议发起，会议查看结果

当前源码路径是录音详情的“更多 → 交给智能体”切换聊天并新建预填草稿；“智能体产物”打开文件列表/QuickLook。当前代码不是会议内直接整理执行器。既有 [2026-10-03 反馈](./recording-ai-actions-feedback-review-2026-10-03.md) 已建议普通整理直接发起，本节沿用这一待评审方向。

首轮从现有聊天执行通知提取、日程创建和会后整理，并提供结构化事项入口；录音详情可作为会后整理的快捷发起入口。所选会议/资料、目标服务和输入限制应可理解，用户主动发起后才运行，任务和结果始终关联来源。后续会议概览可显示“准备参会问题”“整理会议结果”“提取行动建议”并复用同一执行链路，不另建与聊天割裂的智能体。

“继续讨论/自定义要求”进入现有聊天，展示可理解的会议上下文标题和返回来源入口。聊天仍具备通用能力，不只服务会议。固定来源版本、运行关联、结构化结果及完成提交需沿用并补充原契约；不能只改按钮名称，就宣称已经实现直接整理或结构化结果页。

### 13.6 提醒与跨页衔接

会议的个人跟进页完成候选核对后，打开/创建同一个 Yima 待办；提醒编辑页补充会议来源与返回入口。App 中更新后会议页刷新真实状态，可选系统镜像按同步契约接入。提醒页保留现有日历与来源筛选，补齐本地事项编辑，不另开一套专属会议任务管理。

录音期间，查看准备问题、进入聊天或提醒时，已有全局录音状态与停止操作持续可达；不触发第二次采集，也不主动播报。模型配置完成/取消后回到原准备或整理任务；查看原文依据返回时恢复结果位置。系统权限被拒绝时，Yima 日程和待办仍可创建与管理。

### 13.7 状态与视觉一致性

会议内容状态（通知待核对、准备中、文稿处理中、结果待核对）与个人系统事项状态分别展示，不用一个“已完成”覆盖全流程。每个空态说明当前缺什么并提供对应动作；处理失败保留输入，来源变化提示结果所依据的旧版本；缺模型和缺系统权限只影响相应操作。

继续使用系统字体、黑白灰、平铺内容、原生 Sheet 和单列导航。静态走查发现首页筛选已启用时使用红色小圆点，与 `DESIGN.md` 的红色录音/破坏性语义不一致；后续相关页面调整时应改用中性的已筛选提示。此处仅记录规范冲突，本轮未改代码。

无障碍细化应覆盖：概览与来源链接的朗读顺序、字段待核对状态、内容进度的文字解释、大字号下的入口自然增高和横向控件替代、深色模式对比度，以及录音跨页状态。

## 14. 前端交付顺序与验收

根据用户最新明确的效果，先设计并验证聊天、日历、待办之间的两条主流程及来源关系，再判断会议概览和首页扩展的必要性。关键状态与执行结果表达明确后才制作原型和实施；不把整套会议页面改造作为工具联动的前置。

| 交付顺序 | 可评审产出 | 验收重点 |
|---|---|---|
| A 通知到日程 | 本地会议/日程契约、聊天提取、创建回执与两列表入口 | 每会议一个 Yima 日程；无授权也可创建；会议列表与提醒页打开同一对象；缺年份保留待安排；重试不重复创建 |
| B 会议记录到待办 | 本地待办契约、文稿引用、会议整理与个人行动确认 | 整理有依据；确认项创建 Yima 待办；无系统权限也可完成；两处状态一致；未明确日期不猜 |
| C 来源与跨页返回 | 聊天/日程/录音/纪要/待办的关联、刷新和失败恢复规格 | 能回来源；系统编辑/完成/删除如实反映；返回保留上下文；来源筛选保持；录音跨页不中断 |

这是交付草案，不是新建任务或里程碑；A/B/C 不表示工期或版本。通知上下文、系统对象关联及本场录音绑定需要最小数据设计；未来会议排序与会议概览属于后续范围。最终交互仍须与技术契约一起评审。本轮仅补充设计依据和静态页面核对，未修改前端代码或运行设备。

## 15. 已确认核心：Yima 本地能力与三模块联动

### 15.1 会前、会后两条主流程

会前：用户在聊天提供通知并要求安排会议 → 智能体提取标题、时间、地点和说明 → 保存会议及唯一 Yima 日程 → 必要时间信息待核对时保留未安排状态 → 聊天、会议列表和提醒页可打开同一对象。

会后：用户从录音详情或聊天选择会议记录 → 智能体整理摘要、决定、未决与个人行动候选 → 用户确认具体事项 → 保存 Yima 待办并关联会议/日程/依据 → 聊天和待办页可查看、编辑和完成。

两条主流程均无需 EventKit 权限。用户选择系统接入并取得对应权限后，本地日程/待办可关联专属系统列表；本地已保存与系统同步状态分别说明。录音停止后提供整理入口，继续沿用用户主动发起规则。

### 15.2 共享对象与列表来源

| 模块 | 职责与呈现 |
|---|---|
| 聊天 | 提取/整理、追问具体缺项、执行 Yima 操作；展示实际保存的日程/待办摘要、所属列表及可选同步状态；打开对象与来源 |
| 会议列表 | 每场会议关联一个 Yima 日程，显示同一主题与安排；记录、通知、准备和结果归入这场会议 |
| 日历/待办 | 默认可使用“Yima日历”“Yima待办”，再混合授权的系统来源；会议以日程行展示，行动以待办行展示 |

日历和待办继续在现有“提醒”Tab 中呈现。本地来源与系统镜像在 App 内去重，不把会议再复制成一个带完成勾选的同名待办。系统接入后的同步方向尚待用户回复，参见[自有日程与待办设计](./yima-owned-calendar-reminders.md)。

聊天历史回执保留当时实际结果，打开条目后查询当前状态。完成事项不要求自动在聊天插入消息；用户查询时智能体可读取最新状态。

### 15.3 关系、权限与生命周期

最少关系连接通知/来源聊天、会议/唯一 Yima 日程、录音/文稿版本、整理结果及 Yima 待办。Yima 自有内容由本地仓库保存；非 Yima 系统来源由 EventKit 读取。可选镜像保存确切列表与对象映射、版本和同步状态，不能靠同名确认身份。

修改会议安排应更新同一日程；原通知保留原文。无确定日期的会议仍有待安排日程，不猜年份或把它塞入某天。系统权限撤销或镜像不可读不删除本地内容。删除来源录音不默认删除会议日程/待办；会议和日程的删除/解绑需保持明确的一对一关系，具体影响参见独立设计。

用户取消勾选来源只影响提醒页显示，会议列表中的会议仍保留；聊天可直接打开隐藏来源的对象并说明。App 内修改或完成后，相关页面刷新同一个本地对象；系统侧变化如何回写按待确认的同步契约执行。

### 15.4 当前工程与新增交付

静态核对：现有 CalendarOffload/RemindersOffload 操作系统 EventKit，SystemCalendarModel/SystemRemindersView 按系统权限读取，尚未提供独立的 Yima 日程/待办仓库。当前无授权路径会停止读取系统事项，不能作为本地功能已经支持的证据。

新增交付包括本地事务化日程/会议/待办、旧数据迁移、UI/Agent 共用操作、混合来源与去重、跨页关联及可选系统接入。保留原系统工具的来源语义，增加明确的 Yima 操作或路由；不把系统工具失败伪装成本地成功。专属系统列表按稳定 ID 绑定，禁止名称模糊匹配与静默回退；系统标识定位、幂等和保存后回执仍需评审。

本通知缺年份且未提供实际会后内容，本轮记录产品范围和设计，不向用户系统创建样例事项。首轮验收包含两类系统权限均拒绝时的完整本地闭环、每会议唯一日程及两个列表入口、可选授权/撤销/恢复和真实结果表达。不使用模拟器，真机运行另需用户明确授权。
