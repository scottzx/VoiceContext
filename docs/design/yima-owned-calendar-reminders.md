## 2. 目标与边界

智能体从通知创建 Yima 日程，从会后记录创建 Yima 待办。创建、编辑、查看、完成与来源回跳在没有 EventKit 权限时正常工作。系统集成是可选择的能力；本地保存成功与系统同步成功分别报告。

首轮包括两个默认本地列表、会议与日程的一对一关系、会议行动关联、聊天/UI 共用操作服务、混合来源展示及可选系统接入。多人分派、共享日历、自建账号/云同步、周期会议和完整项目管理不属于本轮；不为授权拒绝增加强制注册或付费步骤。

## 3. 统一的数据关系

| 对象 | 最少信息与关系 |
|---|---|
| Yima 日程 | 稳定 ID、所属 Yima 日历、标题、地点/说明、计划起止时间与时区（可待定）、来源、可选 meetingID、修改版本 |
| 会议 | 稳定 ID、唯一 eventID、原通知、来源聊天、关联录音/文稿版本、准备与整理结果 |
| Yima 待办 | 稳定 ID、所属 Yima 待办列表、标题/备注、日期和通知设置（可缺失）、完成状态、可选 meetingID/eventID、依据、修改版本 |
| 系统接入关系 | 本地列表/事项 ID、确切系统来源/列表/对象 ID、上次同步版本或摘要、待同步变更与结果 |

每个会议有且只有一个 Yima 日程；会议列表和提醒页的日程行展示同一对象，不复制成第二个待办。一个会议可以有零个或多个行动待办。普通日程不必是会议，个人录音也不因保存就被强制建会。

会议和日程在同一事务内创建/更新，重试同一创建意图不增加第二个对象。从会议改主题或计划时间应更新同一日程；会议元数据不再平行存一份可独立漂移的当前安排。原通知保留原计划原文，实际录音时间与计划时间分开。

通知缺少年份或日期时，仍建立对应的本地“时间待确认”日程，放在未安排区域；不在日历某天打点，也不尝试导出无有效起止时间的系统事件。补齐日期后更新原对象。

删除录音或整理产物不删除会议日程与行动待办。删除会议/日程的解绑、保留与连带删除选择需在具体交互中说明，首轮默认不连带删除行动事项。若用户只删除日程但保留会议，可将会议安排改为待定；避免出现会议引用不存在日程的静默悬空关系。不可逆处理需要明确操作对象与影响范围。

## 4. 两个本地列表与系统列表

App 始终提供“Yima日历”“Yima待办”两个稳定本地来源；它们默认可选、可写，身份不随系统权限变化。系统日历与提醒权限分别管理：只授权其中一种时，只接入对应类型。

用户开启系统接入并获得必要授权后，为该类型创建或明确绑定对应系统列表。两个默认名称为“Yima日历”“Yima待办”。保存实际来源与列表 ID；存在同名列表时不能按标题自动认领用户已有数据，不能静默回退到另一列表。系统账户只读、不可写或无法创建列表时，保留本地功能并报告接入失败。

本地 Yima 列表与其系统镜像在 App 内合并显示为一个来源、一个事项，来源行可显示“仅本机 / 已连接系统 / 同步待处理”。其他获准读取的系统列表仍是独立来源，继续用 EventKit 读取，不复制成 Yima 本地权威数据。

权限撤销、系统列表不可读或删除，不抹掉本地内容。日历与待办分别暂停受影响的同步；恢复时先核对已有绑定和版本，再处理待同步变更，不再次全量创建镜像。

## 5. 前端与三个基础模块

四 Tab 顺序维持“聊天 / 会议 / 提醒 / 拓展”；本轮未要求独立增加日历 Tab。

| 位置 | 需要的交互 |
|---|---|
| 聊天 | 通知提取后创建 Yima 会议/日程；会后整理后创建所选 Yima 待办；结果显示本地已保存与可选系统同步状态；打开日程/待办和来源 |
| 会议列表 | 显示尚无录音和已有录音的会议，复用同一个日程的主题/时间；进入对应会议内容；保留直接个人录音 |
| 提醒首页/全部 | 日历区、日期分组和来源筛选统一纳入本地与系统事项；会议作为日程行展示，点击打开对应会议/安排；行动作为待办行，可完成 |
| 编辑页 | 新增只提供待办、日程；日程在 Form 内选择普通日程或会议，待办在 Form 内选择保存来源。Yima 事项未授权也可编辑；系统来源继续沿用现有 EventKit 编辑与权限规则 |
| 设置 → 日历与待办 | 提供日历、待办分别接入系统的入口和真实状态；拓展只保留统一设置入口，不在打开提醒页或筛选时强制弹两种权限 |

来源筛选只管理显示哪些来源与是否显示已完成待办，不承担系统接入或申请权限。先展示 Yima 本地列表，再提供已授权系统来源的选择。现有 EKCalendarChooser 只能选择系统列表，本地行需要独立的原生选择项；复用现有系统来源选择器，不伪造 EKCalendar 对象。已经绑定的 Yima 系统镜像应去重展示。来源与显示已完成偏好仍在首页/全部共享并持久保存；用户取消勾选只隐藏内容，不删对象，不因授权变化重置本地选择。

未授权时，日历和待办正常展示 Yima 内容；权限提示位于“设置 → 日历与待办”的系统接入处，不替换整个内容区。两类来源都有事项时继续使用现有红/绿日期点语义：红点计未完成且有到期日期的待办，绿点计有确定日期的日程。未安排会议和无日期待办在相应未安排区域可找到。

会议列表、聊天结果和提醒页指向稳定的 Yima ID，往返保留列表位置和原聊天；事项是否同步到系统不影响来源回跳。提醒页筛选隐藏了 Yima 来源时，聊天仍可直接打开该对象，并解释其列表当前被隐藏。

## 6. 存储、Agent 与通知

建议在 App 私有存储中增加最小的事务化日程/会议/待办仓库，按已有 SQLite 能力评审落点。录音仓库与 ChatStore 保持既有职责，录音不会因日程服务初始化失败而停止采集；成功开录后关联失败须显示状态并可恢复。

Yima 自有事项的新增、读取、修改、完成、删除由 UI 与 Agent 共用同一服务。原 `apple-calendar` / `apple-reminders` 仍表示系统操作，未授权时不会因此获得本地能力；需要新的 Yima 操作入口或明确的来源路由，不能在底层悄悄把系统写入改为本地成功。

Agent 默认将本场会议安排和用户确认的个人行动保存到 Yima 来源。回执必须说明实际保存的对象、所属列表、日期/通知设置，以及系统接入状态。未授权不请求 EventKit、不假称系统已创建；同步失败不撤销已经保存的本地对象。

本地定时通知需要单独的系统通知授权与实现。日历/提醒读取权限被拒绝不阻止本地保存；没有通知权限或仅设置到期日期时，不宣称一定会响铃。系统镜像和本地通知的重复提醒策略需要在通知契约中明确，不能在切换接入时产生双份通知。

## 7. 可选系统同步：待确认的推荐规则

推荐双向同步 Yima 自有列表中的事项：在 Yima 或系统 App 修改日程、完成待办，另一侧最终更新；已有非 Yima 系统列表不纳入自动复制。本节待用户确认同步方向后落实。

- 本地修改先事务化保存并记录待同步操作，再独立尝试 EventKit 写入；失败保留本地结果，显示同步状态。
- 系统修改根据绑定、上次同步摘要和本地版本回写；不能仅凭系统标识变化或一次读取未命中判定删除。
- 同一字段两端都修改时保留两份候选，提示用户选择；没有冲突的字段可合并。系统没有提供可靠完整版本时，不用任意时间戳假装已解决冲突。
- 授权、读取范围、目标列表和绑定均可核实时才处理删除。系统删除镜像日程不能无提示删掉会议通知/逐字稿；保留会议并标注安排需处理。列表整组消失时暂停接入，不批量删本地事项。
- 重复执行、保存成功但回执丢失、系统成功而绑定提交中断等情况，先按原请求/来源标记核对，再恢复关联；禁止盲目重新创建或把同名项当成同一对象。
- 系统列表中直接新增的事项，若采用双向同步，应导入对应 Yima 本地列表并保留来源；普通日程不自动升格为会议。

若用户选择仅导出，系统变更不自动更新本地，应明确显示这是导出副本；后续导出先核对已有映射，不能默认重复创建。该路线也须说明再次导出覆盖规则，不能把两端状态描述为同步一致。

## 8. 权限、隐私与平台依据

App 本地事项不需要 EventKit 读取权限。创建专属系统日历并读取/修改其事项需要对应的系统访问能力；Apple 区分日历无权限、仅写入与完整访问，完整访问才能读取既有日历并创建新日历，不能把仅写入权限当成已支持专属列表管理和双向同步。[Apple EventKit 权限说明](https://developer.apple.com/videos/play/wwdc2023/10052/)

提醒事项接入单独遵循系统授权，不以日历已授权代替提醒授权。[Apple 提醒授权 API](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoreminders%28completion%3A%29)

选择系统来源后，资料可能沿该账户既有同步机制流转；设置需说明所选账户和同步范围。接入权限不表示允许把所有系统安排发送给模型，AI 仍只读取用户主动选定的会议资料。首轮不新增应用云同步，录音默认保留规则不因日程接入改变。

## 9. 迁移与兼容

旧系统日程/提醒仍保留原对象和原来源，不全量复制、不移动到 Yima 列表。初次新增本地来源可默认选中，已有系统来源的取消选择保持；去重基于受管映射而非标题。

对既有明确标为会议的录音，可幂等补充会议与一个 Yima 日程；已知的实际录音时间标明是记录时间，不假装恢复通知中的计划时间。个人录音不自动迁移为会议。已有来源关联和已创建系统事项不能因迁移重复建项；是否将其中某项显式纳入 Yima 管理须另行设计。

## 10. 风格、验证与 PM

风格复用已确认的 `DESIGN.md`（含本轮日程/待办来源与会议投影增补）、系统字体、黑白灰、平铺行和原生 Sheet；不增加新的品牌色或卡片墙。大字号、VoiceOver、44pt 操作区、深色对比度和 Reduce Motion 仍是底线。新本地编辑、来源选择、未安排与同步状态交互需先出规格，再决定原型任务；本轮不制作原型。

核心验收：

- [ ] 两类系统权限都拒绝时，聊天仍能保存 Yima 日程和待办；页面可读取、编辑和完成，重开 App 后保留。
- [ ] 每个会议恰好关联一个日程；会议列表与提醒页打开同一对象，修改主题/时间一致；不会多建一个同名伪待办。
- [ ] 缺年份/日期时有未安排的本地日程，补齐后更新原对象；未有效排期前不导出系统事件。
- [ ] 只授权一类来源时，另一类本地功能继续工作；权限撤销与恢复不删除或重复本地内容。
- [ ] 系统接入后，专属列表绑定准确、列表/事项在 App 中去重；已有筛选与系统来源内容保持。
- [ ] 若确认双向同步，两端修改、完成、删除、冲突、断连恢复与结果不明按已冻结契约验收。
- [ ] 本地保存、系统同步、定时通知分别报告真实结果；本地成功而同步失败不被误报为创建失败。
- [ ] 旧会议补充日程与旧系统关联迁移幂等；直接录音不依赖填写日程；回跳、删除和隐私边界可验证。

实施顺序提案：本地数据/会议关系与迁移 → UI/Agent 共用操作 → 混合来源与关联 → 可选系统列表/同步 → 恢复与验收。各项都需独立的交付说明与验收，排期/版本未提供。本地 PM 服务不可达，未新建或改写看板、功能蓝图、任务和里程碑；新需求 ID 待登记。不使用 iOS Simulator，真机运行须另获用户明确授权。
