# 分阶段声纹处理与前后依赖任务设计

## 文档信息

- 状态：已确认
- Owner：Human / 团队
- 来源需求：#71；状态与交互纠偏：#82
- 对应功能模块：本地语音智能 / 分阶段声纹处理；录音与本地数据 / 前后依赖的双任务进度
- 最后更新：2026-08-28

## 背景与问题

长录音完成 ASR 后，现有收尾路径可能一次性解码全部句段、生成全部声纹锚点、并发计算 embedding，再把完整 observation 集合写成 Pretty JSON。51 分钟真机样本需要处理约 1,865 个锚点，embedding 本身约占 141 秒；期间缺少可持久化进度，PCM 与锚点窗口又会集中驻留内存，因此用户看到的是“转了很久”，系统还存在内存终止风险。

旧任务中心曾将一条录音的 `transcription`、`speakerEmbedding` 和 `speakerFinalization` 聚合成一张卡片。这隐藏了“逐字稿识别 → 声文整理”的真实依赖：逐字稿已完成但下游 job 尚未创建时，聚合卡片会被误算为“进行中”；“全部关停”只能取消已存在的 job，无法为未创建的下游阶段写入取消事实。按整条录音重试或人工完成也会同时改写两个阶段，随后又被后台协调器重算，导致异常、进行中、已完成相互跳转。

## 目标

- ASR 与声纹提取成为两类独立、可重试、可恢复的持久任务。
- 声纹以一个 AudioChunk 或 ProcessingRange 为一次有界工作单元，完成后立即持久化并释放 PCM。
- 待办、进行中、异常和已取消以“录音 + 阶段”为单位；已完成按录音聚合成一张摘要卡，内部按顺序展示已完成的阶段子任务。
- 引入独立“待办”分类：前置依赖未完成或 job 尚在 pending 时属于待办；只有实际拿到执行权且 job 为 running 时才属于进行中。
- 取消、重试和人工完成均按阶段生效；“全部关停”覆盖待办、运行中和异常阶段。
- 现场录音和导入音频在开始处理前显式选择“个人记录”或“多人会议”。
- 个人记录默认跳过声纹计算，并可在录音详情通过现有功能操作区补做说话人识别。
- 会议参会人与已识别发言人分开记录：用户可手工补充未发言或未被识别的参会人，不伪造发言或声纹结果。
- 取消、退后台、温控暂停和进程终止后，不重做已经持久化成功的声纹分片。

## 不做

- 不改变 `SegmentSpeakerAnchorPlanner` 当前每句最多五个锚点及其位置策略。
- 不做字词级时间戳或新的句子切分规则；继续使用明确的句号、问号、感叹号切句结果。
- 不自动推断一条录音是否为多人会议。
- 不在本阶段改造跨会议身份确认算法或聚类阈值。
- 手工添加参会人时不生成空声纹，不将“出席”推断为“已发言”。
- 不让 ASR 与 CAM++ 同时抢占多个高开销模型执行槽。

## 用户、场景或调用方

- 用户录制或导入一条多人会议，先看到逐字稿快速增长，再看到声纹分片逐个完成，最终进入聚类。
- 用户录制个人灵感或独白，选择个人记录后只做 ASR，不消耗 CAM++ 资源。
- 用户后来发现个人记录实际包含多人，在详情操作区点击“说话人识别”补做整条录音的声纹任务。
- 调度器、恢复器、任务中心和录音详情共同消费持久 job 状态，不从动画计时器推测进度。

## 产品流程 / 信息架构

### 新录音

1. 用户点击主界面录音按钮或 Widget 深链。
2. 出现原生选择页，提供“个人记录”和“多人会议”，并简要说明多人会议会增加本机处理时间。
3. 用户选择后才请求麦克风权限并开始录音。
4. 个人记录：closed chunk 仅排入 ASR；多人会议：closed chunk 完成 ASR 后排入对应声纹提取任务。

### 导入音频或相册视频

1. 用户选择来源文件。
2. 文件完成安全访问与基础校验后、正式创建处理任务前，使用同一模式选择。
3. 个人记录跳过声纹；多人会议排入 ASR 与声纹流水线。

### 个人记录补做说话人识别

1. 用户进入录音详情，在现有功能操作区点击“说话人识别”。
2. 二次确认提示本机处理可能耗时、发热和增加耗电。
3. 确认后把该 Recording 切换为允许声纹处理，并为已有可处理来源补齐 `speakerEmbedding` jobs。
4. 已完成观察值幂等复用；任务中心立即显示声纹进度。

### 手工补充参会人

1. 用户进入会议详情的“参会人与声纹”，点击标题旁“添加参会人”。
2. 用户可仅输入本场姓名，或选择已有全局客户档案；两种方式都不要求存在声纹。
3. 未发言参会人显示“已参会 · 暂无发言声纹”，不进入逐字稿的说话人筛选和分句归属。
4. 后续若某个已识别发言人确认绑定到同一客户档案，列表合并为一人，参会记录仍保留。
5. 手工参会名单写入会议的本地 JSON/Markdown，重新转写只清理派生的说话人结果，不清理参会名单。

### 任务中心

- 列表单位是一个用户可操作的阶段任务，不展开分钟分片。
- “逐字稿识别”卡显示 ASR x/y；“声文整理”卡显示声纹 x/y 和聚类状态。两张卡共享录音标题，但有独立的阶段名、状态和操作。
- “已完成”分类改为按会议或文件展示：卡片标题是会议/文件名，下方为编号子任务。第 1 项为“逐字稿识别”，如果启用声文则增加第 2 项“声文识别”；每项显示完成数量和完成时间。
- 顶部分类为：待办、进行中、异常、已取消、已完成。`pending` 和“前项未完成”都显示为待办，`running` 才显示为进行中。
- 声文整理在逐字稿未完成时显示“待办，等待逐字稿识别”；只有前项完成后才能领取 speaker job 并进入进行中。
- 长按菜单按阶段提供“取消任务 / 标记为已完成 / 重新开始”；操作一张卡不得改写另一张已完成卡。
- “全部关停”必须为未实例化的下游阶段补一条可持久恢复的 cancelled 占位 job，否则待办任务会在刷新后再次出现。

## UI/UX 风格确认

- 状态：已确认，复用仓库根目录 `DESIGN.md`。
- 一句话记忆点：安静、可信地告诉用户每条录音做到哪一步。
- 风格关键词：Apple 原生、克制、内容优先、状态诚实、低干扰。
- 反向关键词：卡片堆叠、仪表盘炫技、虚假动画进度、AI 渐变、过度技术术语。
- 原生与品牌：以原生 `confirmationDialog` / sheet、List、ProgressView 和系统语义色为主。
- 信息密度与层级：一个阶段一行扁平任务卡；阶段名与录音标题优先，进度与依赖说明次之，系统温控信息放辅助区域。
- 视觉方向：系统字体与 SF Symbols；颜色只表达运行、成功、警告和失败；尊重 Reduce Motion。
- 无障碍底线：动态字体不截断关键计数；VoiceOver 读出每阶段完成数、总数和状态；不能只靠颜色区分；触控目标至少 44pt。
- 决策记录：用户于 2026-08-26 确认复用现有设计方向；2026-08-28 根据真机操作结果，明确取消“一条录音一张聚合卡”，改为两张前后依赖任务卡并新增待办分类；同日确认参会名单不能仅由发言人识别结果推导。
- 既有规范：`DESIGN.md` 的 Typography、Color、Layout、Motion、Accessibility 和禁止模式。

## 原型与 UI/UX

不单独制作低保真或高保真原型。原因是开始模式选择、任务聚合行和详情操作均复用现有信息架构与原生组件，没有新增导航层级；必须通过 SwiftUI Preview、UI 测试和真机设计走查覆盖正常、空、处理中、失败、个人跳过、动态字体、VoiceOver 与 Reduce Motion 状态。

## 技术方案

### 任务图

每个来源单元形成以下依赖：

```text
AudioChunk / ProcessingRange
  -> transcription job
  -> speakerEmbedding job（仅启用说话人识别时）

全部需要的 speakerEmbedding jobs 完成
  -> speakerFinalization job
  -> 聚类、说话人 turn 与文档发布
```

- `speakerEmbedding` job 与其来源保持一对一，通过 `chunkID` 或 `processingRangeID` 识别。
- 对正在录音的多人会议，ASR 完成一个来源后即可创建/唤醒对应声纹任务；实现可先串行执行，避免模型并发放大内存。
- `speakerFinalization` 只消费已经持久化的 observations，不再回退为“整条录音一次性重算”。兼容旧录音时，由补任务/迁移过程生成缺失的 `speakerEmbedding` jobs。
- job claim、execution token 和 lease 延续现有机制，迟到结果不得覆盖重试后的新执行。

### 有界声纹工作单元

1. 读取一个来源对应的已提交句段。
2. 只解码该来源当前需要的 PCM 范围。
3. 按现有锚点规划器生成窗口。
4. 在固定小并发 worker 池中计算 embedding；每批间检查取消和 lease。
5. 用来源 id 作为 batch key 原子替换 observation batch。
6. observation 落盘成功后标记 job 完成并释放 PCM/窗口数组。

### 存储

- 热路径禁止 `.prettyPrinted` 和 `.sortedKeys`。
- 每个来源一个紧凑 JSON batch，使用临时文件 + replace 原子提交；旧的整文件 `observations.json` 仅兼容读取，不再由新热路径写入。
- `replaceBatch` 保持幂等，同一来源重试覆盖自己的 batch，不影响其他来源。
- 后续若紧凑 JSON 仍成为瓶颈，再以独立迁移评估 Float32 二进制格式，本阶段不提前引入第二种新格式。

### 调度与资源

- ASR 优先保证逐字稿及时性；声纹任务在无待执行 ASR 或策略允许的间隙运行。
- 默认同一时刻只执行一个来源的声纹提取；单来源内部 worker 数保持有界，不为每个来源重新常驻多份模型。
- 进入后台、用户全部关停、温控严重或 lease 失效时，在来源和 embedding batch 边界取消。
- 取消中的未提交 batch 不计完成；此前成功 batch 保留。

## 数据与接口

- `Recording.isMeeting` 只表示产品类型；`Recording.speakerProcessingEnabled` 独立表示是否执行声纹阶段。
- 旧日志或旧 SQLite 行缺少该字段时默认为开启，保持升级前“所有录音都会整理说话人”的历史行为；只有新建并明确选择“个人记录”的数据才关闭。

- `Recording.isMeeting` 继续作为处理模式的持久快照：`true` 表示启用多人说话人处理；`false` 表示默认跳过。
- 补做说话人识别时将录音更新为 `isMeeting=true`，写入 journal，并补齐缺失任务。
- `RecordingJobKind.speakerEmbedding` 使用现有 jobs 表，不新增平行任务表。
- `TranscriptDocumentV1.participants` 保存手工确认的参会名单快照，包含稳定 id、可选全局客户 id、姓名、组织/职务与添加时间；旧文档缺少字段时按空数组解码。
- `speakers` / `speakerTurns` 仍只表示从音频推导的发言人，不将无发言参会人写入该字段。
- 新增面向 UI 的阶段任务快照，至少包含：
  - recording identity/title/update time；
  - stage identity（transcription / speakerProcessing）与确定性卡片 id；
  - 阶段状态（todo / running / failed / cancelled / completed）；
  - completed/total/running/pending/failed/cancelled；
  - 下游依赖说明、finalization state 和最近错误。
- 分母取该 Recording 已规划并应处理的 AudioChunk 或 ProcessingRange 数；最终未满一分钟分片关闭后分母随之增加。UI 展示真实计数，不展示估算百分比。

## 状态、错误与恢复

- 个人记录：speaker 状态为 `skipped`，不创建空任务。
- ASR 尚未完成：声文整理阶段为 `todo`，对应 speaker job 可不存在或 pending，不提前解码。
- ASR job 为 pending：逐字稿卡为 `todo`；只有 ASR job 为 running 才是“进行中”。
- 用户全部关停：取消所有未完成 job；多人录音若尚无 speaker job，创建 cancelled `speakerFinalization` 占位作为“下游阶段已取消”的持久事实。
- 重新开始：逐字稿未完成时先恢复 ASR，声文整理仍保持待办；ASR 完成后再由 reconciler 放行 speaker processing。
- 用户对逐字稿执行“重新转写”时，按完整依赖链级联重置：先失效旧 ASR 执行，再将全部 transcription、speakerEmbedding 和 speakerFinalization job 回到 pending，完成计数立即归零。清空旧逐字稿 segment、本场说话人绑定、observation batches 和最终整理指标，但不删除原始音频或全局长期声纹档案。
- 手工参会名单是用户事实，不属于可重算声纹派生物；重新转写、声纹重试与最终聚类不得删除它。
- 级联重置后，声文整理保持待办并显示“等待逐字稿识别完成”；全部 ASR job 完成后必须由 reconciler 自动放行新的声纹提取与最终整理，不要求用户再点一次声文任务。
- 某来源失败：只重试该 `speakerEmbedding` job；其他来源完成数保留。
- 进程终止：运行中 job 由现有恢复机制回到可重试状态，已写 batch 不回滚。
- observations 已有而 job 状态缺失：恢复器核对 batch key 后可将任务补记完成，避免重复 embedding。
- observations 缺失而 job 被误记完成：一致性检查把该 job 重新排队。
- 最终聚类失败：不清空 embedding batches，只重试 `speakerFinalization`。
- 用户在详情补做：允许从 0/y 开始，也允许复用旧录音已有 observations。

## 隐私、安全与合规

- 所有音频、PCM、embedding 和聚类均在本机处理。
- 模式选择文案说明多人会议会进行额外本机声纹计算，不暗示身份自动确认。
- 个人记录不会偷偷计算声纹；只有用户选择多人会议或明确点击补做后启用。
- 删除 Recording 时沿用现有删除流程移除 jobs 和 observation batches。

## 验收标准

- [ ] 52 分片多人录音在任务中心显示两张阶段卡：逐字稿识别 x/52，声文整理显示声纹 x/52 与聚类状态。
- [ ] 任务中心有独立待办分类；pending 或依赖未满足不再计入进行中。
- [ ] 已完成分类每个会议/文件只显示一张摘要卡，标题为录音名，子任务按“1. 逐字稿识别”和可选“2. 声文识别”显示完成数量与时间。
- [ ] 声文整理只在逐字稿识别完成后进入 running；取消、重试和人工完成不跨阶段误改已完成任务。
- [x] 点击逐字稿“重新转写”后，逐字稿与声纹阶段完成数同时归零，旧文字和本场声文结果被清除；新逐字稿完成后声文识别自动开始。
- [x] “参会人与声纹”可添加仅本场姓名或已有客户；无发言者显示“已参会 · 暂无发言声纹”，不出现在逐字稿说话人选项中。
- [x] 参会名单在 JSON/Markdown 中可恢复，并在重新转写、声纹重试后保留；同一客户后续确认为发言人时界面不重复展示。
- [ ] 全部关停可处理下游 job 尚未创建的待办任务；刷新、恢复或应用重启后不会自行回到进行中。
- [ ] 每完成一个来源的声纹提取即持久化并推进计数；强杀重启后从未完成来源继续。
- [ ] 处理一个来源结束后不再保留整条录音的句段 PCM 和全部锚点窗口。
- [ ] 新热路径不写 Pretty JSON；旧 observations 可继续读取。
- [ ] 取消、后台、温控和 lease 失效在有界边界响应，不提交迟到结果。
- [ ] 现场录音、Files 音频和相册视频均在处理前选择个人记录或多人会议。
- [ ] 个人记录显示“说话人识别：已跳过”，且详情可补做；补做后任务进度立即出现。
- [ ] 锚点数量、位置和聚类算法输出在相同输入下不因流水线改造而改变。
- [ ] 使用“云深处”约 52 分片真机录音验证进度、恢复、总耗时与峰值内存，并保存可审计证据。
